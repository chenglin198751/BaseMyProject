# Crash 修复

## 目标

1. 分析 crash 日志
2. 找出 crash 根本原因
3. 给出修复方案
4. 在用户确认后再修改代码

---

## 核心规则（强制）

- 默认不修改代码
- 必须先完成分析，再等待用户确认
- 未得到明确确认前，禁止执行任何代码修改（Edit 工具）
- 如果无法确定 crash 原因，必须说明“不确定”，禁止给出修复方案

---

## 执行流程（两阶段）

### 阶段 1：分析（默认执行）

输出内容：

1. crash 类型（如 NPE / IndexOutOfBounds 等）
2. 关键堆栈位置
3. crash 根本原因（必须结合堆栈具体分析）
4. 触发条件（在什么情况下发生）
5. 修复方案（仅在原因明确时输出）
6. 修复风险等级（高 / 中 / 低）

最后必须输出：

是否执行修复？（仅当用户明确表示“确认”或等价指令时才允许进入下一阶段）

---

### 阶段 2：修复（仅在用户确认后执行）

触发条件：

- 仅当用户明确表示“确认”“修复”或等价明确指令时才允许进入修复阶段

输出内容：

- 按方案修改代码（使用 Edit 工具写入源文件）
- 简要说明修改内容
- 评估是否修复了根因（附判断依据）
- 若修复完成，输出：✅已按方案完成代码修改。并换行输出一条简洁的 git commit message（仅提供文本）
- 是否存在风险（🔴高 / 🟡中 / 🟢低）
