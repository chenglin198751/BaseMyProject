# 代码重构

## 重构原则

重构的本质是**改善代码内部结构，不改变外部行为**。

## 第一步：识别并锁定 public API

**默认作用范围：仅限当前指定的文件，不主动修改任何其他文件。**
若重构过程中发现其他文件也需要调整，先列出来告知用户，等待确认后再处理。

在动任何代码之前，先列出以下内容（后续不得修改）：

- public class / interface
- public method 及其签名（参数类型、顺序、返回值类型）
- public 字段与常量

## 第二步：分析问题

逐一说明代码存在的问题，例如：

- 方法过长 / 嵌套过深
- 命名不清晰
- 重复逻辑
- 潜在 bug 或空值风险
- 注释缺失或过时

## 第三步：说明重构方案

在修改前，简要描述将进行哪些改动及原因。

## 第四步：必须直接在原文件上完成重构代码，而不是输出代码

### 允许的改动

| 类型 | 示例 |
|------|------|
| 提取方法 | 将长方法拆分为私有辅助方法 |
| 简化嵌套 | 用 early return 减少嵌套层级 |
| 改善命名 | 私有变量、内部方法重命名 |
| 删除冗余 | 去除无用代码、死代码 |
| 增加防御 | 补充必要的空值检查 |
| 修复 bug | 修复明显错误或潜在隐患 |
| 优化注释 | 新增或改善注释，**不得删除原有注释** |

### 绝对禁止

- 修改任何 public API（签名、返回值、字段名、常量值）
- 改变代码对外可观测的行为
- 引入新的依赖库
- 进行微优化或性能优化
- 对不确定是否安全的地方做修改（遇到疑问，列出来告知用户，不要静默跳过）

## 输出格式

1. **问题清单**：当前代码存在哪些问题
2. **重构方案**：将进行哪些改动
3. **完整代码**：可直接复制使用的完整代码，不输出局部片段
4. **变更确认**：
   - public API 对比（重构前 vs 后，确认一致）
   - 如有 bug 修复，逐条说明
   - 如有跳过未改动的地方，说明原因
